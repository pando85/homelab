    vnext ablations: real voice is what moves the needle (2026-11-08)

    Source: recovery plan P1 (source attribution) and P2 (candidates), run ahead of schedule because the real recordings arrived the same morning, plus the first room evidence for P3. Follows the P0 real-voice baseline. Everything ran offline on the workstation (~/kivi-models/data/vnext/). The result of this note is deployed: the chosen head is h_c120_w64, released as oye_kivi_next v5-oye-kivi-2026-11-08, trialled on c3-a from 2026-11-08 and, by the owner's decision of 2026-11-11, the wake word of the household pipeline "Kiwi" for every satellite (Deployment).

    Bottom line: consented real positive takes move recall on unseen real takes from 25 % to 75 % on the satellite at a lower measured room false-wake rate (0.12/h against 0.96/h), and the real confuser takes drop from 10/54 to 1/54 (0/54 for rn_rp_h, the head that got closest on synthetic data). No front-end filter helps (the model was the problem), and more augmentation of the same 40 cues does nothing — the next improvement has to come from new recordings: a test-split session on a later day, spk02, and ~15 h per device of fresh room exposure. The head that shows this (h_c120_w64) is released as oye_kivi_next v5-oye-kivi-2026-11-08, the household wake word since 2026-11-11.

    Arms

    All arms share the vnext synthetic set (59,973 positives, 59,976 negatives from vnext_oye_kivi.yaml, the strict-target recipe) and the same ACAV / MLS / hard-negative / room-negative mix as v4's selected arm. They differ only in the real inputs:

    Arm Real negatives Real positives Warm start
    vn_ws4k_v4real v4's set (predates the confuser session) none v2 head, 4k steps
    vn_ws4k_rn refreshed: 31 old-"kivi" + 66 near-word + 83 background rows per source none v2 head, 4k steps
    vn_ws4k_rn_rp refreshed all 232 takes (leaks the evaluation session) v2 head, 4k steps
    vn_sc4k_rn refreshed none fresh head, 4k steps
    vn_ws6k_rn_rp refreshed all 232 takes v2 head, 6k steps
    vn_ws4k_rn_rp_h, _h3 refreshed session 1 only, session 2 held out v2 head, 4k steps, seeds 2 / 3

    Selection threshold per arm = the point that leaves 2 false activations on the 8.377 h of room selection audio (0.24/h); the room test parts were never used here.

    Result 1: confuser negatives without real positives destroy recall

    Real-take acceptance (all 232 take-sources, satellite + desk mics) at each arm's own threshold:

    Arm Real takes accepted
    vn_ws4k_v4real (no real positives) 58/232 = 25 %
    vn_ws4k_rn (+ 5.5x more real confuser negatives) 3/232 = 1 %
    vn_ws4k_sc4k_rn (fresh head) 0/232 = 0 %
    vn_ws4k_rn_rp (real positives, leaky) 209/232 = 90 %
    vn_ws6k_rn_rp (real positives, leaky, 6k steps) 214/232 = 92 %

    The synthetic selection metrics hide this: vn_ws4k_rn scores better on the synthetic held-out set than the control (clean 0.678 vs 0.691 is a wash, val_pos 0.395 vs 0.343) while collapsing to 1 % on real speech, and its acceptance of the real confuser windows drops 50x (0.0051 -> 0.0001). Pushing the confusers down with real negatives only works if the model also has real positives to tell them apart from; the recipe change is the pair, not the negatives.

    Result 2: generalisation to unseen real takes (the honest number)

    vn_ws4k_rn_rp is leaky — session 2 is in its training set. So session 2 was held out entirely (v3_real.py feats --holdout-session, new: (block, cue) collides across sessions because every block numbers its cues from 1) and retrained at two seeds. Session 2 = 40 cues x 3 sources = 113 usable take-sources, never seen in training.

    Scored with kivi_score.py on the session's stored clips, satellite tv-c3a (what the server hears), each model at its own selection threshold:

    Condition v4 (deployed) control (no real pos) rn_rp_h rn_rp_h3 Gate
    TV off (1.5 m + 3 m) 7/20 = 35 % 9/20 = 45 % 14/20 = 70 % [48, 85] 15/20 = 75 % [53, 89] >= 80 %
    TV on (1.5 m + 3 m) 3/20 = 15 % 4/20 = 20 % 14/20 = 70 % [48, 85] 13/20 = 65 % [43, 82] >= 60 %
    ALL 10/40 = 25 % 13/40 = 32 % 28/40 = 70 % [55, 82] 28/40 = 70 % [55, 82] —
    Desk mic, ALL 11/40 = 28 % 11/40 = 28 % 27/40 = 68 % 31/40 = 78 % —

    Per cell (satellite, 10 takes each): rn_rp_h 1.5 m TV off 10/10, 1.5 m TV on 7/10, 3 m TV off 4/10, 3 m TV on 7/10; rn_rp_h3 10/10, 5/10, 5/10, 8/10. (Wilson 95 % intervals on the pooled cells.)

    Real positives take unseen real speech from 25 % to 70 % on the channel that matters, with the same room-false-wake budget as the selection gate. The TV-on gate (>= 60 %) is met at both seeds; TV-off (>= 80 %) is not — 1.5 m is saturated (10/10 both seeds) and the deficit is entirely at 3 m with the TV off (4/10 and 5/10), which is the odd-cell-out and the thing to attack next.

    Result 3: the mic chain is not the bottleneck (P1 source attribution)

    The same session-2 takes, scored on the satellite's own raw wake stream, and on filtered copies of that stream (ha_filter_mirror.py, the trees extended with today's sessions: 3 files written, 50 skipped):

    Path (identical takes) v4 (deployed) at 0.9437 rn_rp_h at 0.97125
    satellite, as recorded 10/40 = 25 % 28/40 = 70 %
    + RNNoise 12/40 = 30 % 26/40 = 65 %
    + second WebRTC NS pass 7/40 = 18 % 28/40 = 70 %
    desk mic (clean reference, no satellite) 11/40 = 28 % 27/40 = 68 %

    Every difference is inside the noise of 40 takes (+-2 to +-3 cues, intervals +-15 points wide), and the clean desk mic is no better than the satellite. No front-end profile change is indicated: the plan's "no signal-processing change without a matched-model replay result" holds — the matched replay shows the model explains the gap, the chain does not. Not re-run here: the speex mirror (its Nov 7 result stands); pyspeex_noise is not installed in either workstation venv anymore.

    Result 4: recipe knobs on the same 40 cues do not help

    Both knobs were tried with session 2 still held out (4 arms, vnext/runs4.sh):

    Arm Real windows per take Real share of positives/step Holdout accepted Train accepted
    vn_h_c40_w32 (= rn_rp_h, re-run) 4,760 64/256 79/113 114/119
    vn_h_c40_w64 4,760 128/256 78/113 116/119
    vn_h_c120_w32 14,280 64/256 78/113 105/119
    vn_h_c120_w64 14,280 128/256 80/113 117/119

    The re-run reproduced the original arm exactly (same threshold 0.97125, same 79/113), so the pipeline is deterministic — and tripling the augmentation variety or doubling the real sampling weight moves the holdout by one or two takes out of 113. The limit is the diversity of the 40 cues, not the recipe. More recordings, not more tuning.

    Result 5: the confusers are fixed on real speech

    All 54 consented real near-word takes (sessions 1 and 3, satellite, each model at its own selection threshold):

    Near-word v4 (deployed) control (v4's real negatives) rn_rp_h
    oye Fifi 4/6 0/6 0/6
    oye kiri 3/6 2/6 0/6
    oye kili 2/6 1/6 0/6
    oye tivi 1/6 1/6 0/6

    oye mira / oye tú / o sea / hoy vi 0/6 each 0/6 each 0/6 each
    ALL 10/54 = 18.5 % 4/54 = 7.4 % 0/54

    The core phrase goal still holds ("kivi" alone never triggers), and the candidate's confuser acceptance is zero in 54 trials — with 0 events the 95 % upper bound is still ~5.6 %, so this is not a room false-wake rate: that needs the room test replay (Next item 3), not 54 prompted takes.

    Result 6: the same candidate on the untouched room test part

    v3_room.py score --part test (8.31 h: 4.11 h c3-a, 4.20 h c3-b; never used for selection, each model at its own threshold, 2 s refractory, exact Poisson intervals):

    Model c3-a c3-b pooled per hour [95 % CI]
    v4 (deployed) at 0.9437 2 6 8 0.96/h [0.42, 1.90]
    control at 0.95435 1 2 3 0.36/h [0.07, 1.06]
    rn_rp_h at 0.97125 1 2 3 0.36/h [0.07, 1.06]

    The v4 row reproduces the published room figure exactly, which validates the replay chain. The candidate is 3x under it in point estimate (and 10 events at 0.9437, one event more than v4: its score distribution sits higher, so it is not a model you may leave at the old threshold — the threshold comes with the model).

    This does not meet the gate yet. 0.36/h [0.07, 1.06] cannot exclude the 0.25/h budget, and per device c3-b is 0.48/h [0.06, 1.72]. Roughly 15 h per device with no events would be needed for the upper bound to fall under 0.25/h, so the room exposure has to be collected over the coming days, not squeezed out of the existing pieces.

    Result 7: the three heads side by side, and the one that shipped

    Session 2 was held out of training for all three heads, so the satellite channel of that session is the honest generalisation number. Each head is scored at its own selection threshold (v4_select.py, <= 2 false accepts in 8.377 h of room selection part):

    Head raw thr TV off TV on ALL (40 takes) Confuser takes, satellite (54) Room test part (8.31 h)
    v4 (deployed) 0.9437 7/20 = 35 % 3/20 = 15 % 10/40 = 25 % 10/54 = 19 % 8 = 0.96/h [0.42, 1.90]
    rn_rp_h 0.97125 14/20 = 70 % 14/20 = 70 % 28/40 = 70 % 0/54 3 = 0.36/h [0.07, 1.06]
    rn_rp_h3 0.96408 15/20 = 75 % 13/20 = 65 % 28/40 = 70 % 1/54 3 = 0.36/h [0.07, 1.06]
    h_c120_w64 0.9754 15/20 = 75 % 15/20 = 75 % 30/40 = 75 % 1/54 1 = 0.12/h [0.003, 0.67]

    Per cell for the chosen head (10 takes each): 1.5 m TV off 10/10, 1.5 m TV on 7/10, 3 m TV off 5/10, 3 m TV on 8/10. On the session's other microphones it is 32/40 (pc-mic) and 31/40 (webcam-mic).

    The confuser column pools both near-word sessions on the satellite (session 1: 18 cues, session 3: 36), as Result 5 does. In the dedicated confuser session alone (session 3, 36 takes) the new heads are 0/36 against v4's 8/36; the single acceptance of h_c120_w64 in the pooled 54 is "oye kili" once on session 1's near block, which was in its own training data — a fitting gap rather than a generalisation failure. The same word also reaches the trigger once on each of the two PC reference microphones of session 3, so "oye kili" stays in the negative pool at confuser weight. The held-out session's own near block is 0/9 on every channel and every model.

    Why this one. rn_rp_h3 is marginally ahead on the window-level all-microphone measure (82/113 against 80/113) while h_c120_w64 is ahead on the deployment channel (30/40 against 28/40): two takes out of 40, which is noise. The tie-break was behaviour at the operating point that would actually be served — one room event in 8.31 h against three. The heads are inside the margin that Result 4 measured for these recipe knobs (one or two takes out of 113), so this is a choice among near-equals, not evidence that the knobs matter; and the room part had already been inspected for v4 and rn_rp_h, so using it as the tie-break costs a little of its independence.

    The threshold is not transferable. At v4's raw 0.9437 this head accepts 8 events in the same room test audio (and rn_rp_h accepts 10): their score distributions sit above v4's. The artefact is the pair (model, threshold), which is why calibrate bakes 0.9754 into the final bias.

    Deployment: oye_kivi_next v5-oye-kivi-2026-11-08, one TV

    wake_release.py ran the full flow for h_c120_w64 as model id oye_kivi_next, version v5-oye-kivi-2026-11-08, raw threshold 0.9754 = the server's default 0.5, served oye_kivi_next.tflite sha256 3101e61eb8d55faa37623c8fe7eda30cc1b9f3982c37bf393c85bce49fac93ae, image git.grigri.cloud/agil/kivi-models:v5-oye-kivi-2026-11-08@sha256:3a198f7d4958 (anonymous pull refused, CI run checked). The release state keeps the score and gate JSON: ~/kivi-models/data/releases/v5-oye-kivi-2026-11-08/.

    • Gate: INCOMPLETE, exactly as the data predicts — the room checks pass at the point estimate (0.12/h pooled, 0.0/h on c3-a, 0.238/h on c3-b) and the recall checks have no rows because all three real sessions are train split and there is only one speaker. Released with the owner's reason (--accept-gate-fail), not as a pass.
    • New id, not an overwrite. v4's oye_kivi file is still served: the household pipeline "Kiwi" keeps oye_kivi, and the recovery plan's rule for a gate that does not pass — trial on one device — is only possible because the candidate has its own id. A trial pipeline "oye Kivi" (a copy of the preferred one, wake word oye_kivi_next) ran on c3-a only from 2026-11-08 11:56 UTC.
    • Household wake word since 2026-11-11 (owner decision). The owner asked for the latest model on all satellites through the global pipeline and no per-satellite overrides: "Kiwi" (preferred) uses oye_kivi_next, both satellites' pipeline selects (both the first and the second select of each) are preferred, and the trial pipeline "oye Kivi" no longer exists. The gate stays incomplete; the owner's reason is in the release state's promotion.owner_override. The change was found live on 2026-11-11 and was recorded afterwards by promote --previous-wake-word oye_kivi (no Home Assistant write by the driver). With nothing pointing at a non-preferred pipeline, a Home Assistant restart can no longer restore a select to a trial pipeline (it can only fall back to preferred, which is the intended state).
    • Rollback: wake_release.py demote --version v5-oye-kivi-2026-11-08 (no approval needed): "Kiwi" goes back to v4's oye_kivi, the previous household wake word. The evidence in "Next" is still missing.
    • Model card in kivi-models records the numbers, notes.md the caveats; licence notes were re-issued for this version because it is the first model here trained on a household member's positives.
    • The three dataset sessions were adopted into the release state (extract --adopt-session <session>) instead of re-extracting already-aligned audio, which would have made a new revision and superseded the marks the training data refers to.

    Result 8: the first clean held-out session (2026-11-11, odd date, PC and webcam channels only)

The TV mic stays the gate for the deployed TV path. Day split unchanged: odd dates test, even dates train. Old manifest rows are not rewritten: eval_channel is derived from (source, split) everywhere (kivi_real_common.is_eval_channel).

    Session 20261111T171918Z-spk01-tv-c3a (spk01, c3-a, split test, 9 blocks, 101 cues, 9.2 min, cues every 3.5 +-0.5 s, later day than every training and selection input of v4 and v5).     What this does not prove

    • One speaker, one day. Sessions 1 and 2 are 14 minutes apart, so the holdout measures continuity within a morning, not across-day or across-speaker robustness. spk02 is absent from the real data entirely (the gate needs >= 2 speakers).
    • 20 takes per held-out condition — intervals are +-19 points wide.
    • The confuser result (0-1/54) and the room replay are different evidence. 54 prompted takes say nothing about rate per hour; 8.3 h of room audio cannot exclude 0.25/h (Result 6), and that part was already inspected for v4, so it is not a fresh unbiased test either.
    • The --holdout-session windows still let session 2's 6 background segments per source into the negative pool (room noise, no speech); its takes and near-words do not (its near block is marked excluded).
    • Selection thresholds come from the room selection parts at 2 events / 8.38 h. Session 2 has now informed a pick (Result 7), so it is a holdout that has been looked at, not a fresh test set: it estimates generalisation to an unseen session, but the choice among close heads used it, so the 75 % is mildly optimistic as a promise about tomorrow. The test-split session on a later day is the number that settles it.
