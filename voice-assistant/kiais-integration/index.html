    Kiais as the Kivi conversation agent in Home Assistant

    Status: VERIFIED on a throwaway local Home Assistant 2026.10.4 (same image as production); DEPLOYED to production on 2026-11-05 with the owner's approval (see Deployed 2026-11-05). Date: 2026-11-05 Scope: how the production Home Assistant (2026.10.4, apps/home-assistant/) should talk to the Kiais gateway (fast tier) as the agent behind the "Kiwi" pipeline, with built-in intents first. Risk of the work done: nothing changed in the production Home Assistant, the cluster or git-applied state. Read-only checks on production: the custom components folder, the agent config entries and pipelines (domains and names only), and one unauthenticated GET /v1/models from the Home Assistant pod. Two local sessions sent about 190 chat requests with synthetic Spanish text to Kiais fast over the public URL; the key was the owner's existing client key, loaded into an environment variable for the run only.

    Evidence labels: documented (read in source code at the version named), observed (seen on the live system or the gateway on the date above), verified (run end to end on the throwaway Home Assistant), inferred (reasoned from the above, not run).

    Correction: the first version of this page said Home Assistant 2026.10.4 has no core OpenAI-compatible conversation integration. That was wrong: core ships litellm and llama_cpp, both of which take a base URL and speak /v1/chat/completions. Both were tested in a second session and the recommendation changed.

    Recommendation

    1. Use the core llama_cpp integration ("llama.cpp", in core at 2026.10.4, quality scale bronze) pointed at Kiais. Verified on 2026.10.4 against Kiais fast: it streams, uses Home Assistant's Assist LLM API (intent tools and GetLiveContext), keeps follow-ups, and every control turn changed the right entity. Its stream parser is not affected by the Kiais quirk (see below). It needs no code, no HACS and no GitOps change: only UI configuration. Its latency matched our own component's within noise.
    2. Pipeline "Kiwi": agent llama.cpp "Fast" (model fast), "Prefer handling commands locally" on (prefer_local_intents), Spanish prompt below, Assist API on, temperature 0.2, maximum tokens 300.
    3. The same integration can later point at a local llama.cpp server (for example a small model on the GTX 1060 that another study is looking at) as a second entry, with no change to the approach (inferred: same OpenAI-compatible API; the integration was written for llama.cpp's server).
    4. Keep kiais_conversation (our prototype, in scripts/voice-assistant/custom_components/kiais_conversation/) only as a reference and fallback, not deployed. It would be worth deploying only if a gap below starts to matter (timeouts, history trimming, a Spanish error message).

    Gaps of llama_cpp to accept (documented, 2026.10.4 source):

    • Timeouts and retries are the OpenAI SDK defaults (openai 3.10.0: read timeout 600 s, 2 retries) and have no option; a hung backend would keep a voice turn open until Kiais' own stream idle timeout (300 s) or the satellite gives up.
    • No history limit: the whole chat log of the conversation is sent (Home Assistant drops idle conversations after a few minutes, so voice conversations stay short; inferred).
    • Streaming support is detected once in the config flow (a streamed test request with tools); it was detected as supported for Kiais (observed).
    • On a gateway error the pipeline gets a generic Home Assistant error, not a spoken Spanish fallback.

    Confidence: high that it works (verified end to end on the production image with the real gateway, 68 turns per agent over the two runs); medium on latency (one afternoon, one gateway backend).

    3. The Kiais stream quirk, exactly

    One raw streamed tool call from Kiais fast (observed, served by kimi-k2.5 on alibaba-coding-plan at the time): the first chunk carries role, id (functions.intent__HassTurnOn:0), index 0, type and the full name; every following chunk again carries the full name and type, and id as an empty string, plus the next piece of arguments; the last chunk has an empty delta and finish_reason: tool_calls. OpenAI sends the name and id only in the first chunk.

    What this breaks, by parser:

    • A parser that concatenates every name piece (name += delta.name) gets intent__HassTurnOnintent__HassTurnOn... and the tool call fails (this is what broke the first version of the evaluation harness).
    • A parser that overwrites the id whenever the field is present (id = delta.id, not checking for an empty string) ends with an empty tool call id.
    • llama_cpp (core) is not affected (documented and verified): it takes id and name from the first chunk of each index and only appends arguments for later chunks of the same index. litellm does not stream, so it never sees the chunks. local_openai and kiais_conversation only take a name that differs and an id that is non-empty.
    • Residual risk in llama_cpp (documented, not triggered): it reads only tool_calls[0] of each chunk and stops at the first chunk with a finish_reason, so a backend that packs two tool calls into one chunk, or puts the last text in the finish_reason chunk, would lose data. Kiais sent the two calls of "Enciende la cafetera y la luz de la cocina" in separate chunks and both ran.

    A gateway fix is still worth it for robustness, since other backends of the tier may behave differently: Kiais could normalise streamed tool calls to the OpenAI shape (send id, type and name only in the first chunk of each index, omit them afterwards). No component of ours is needed for that.

    Findings (verified unless marked):

    • prefer_local_intents works as documented: 5 of 17 turns were answered by built-in intents in at most 0.45 s (both sessions), with no Kiais request.
    • Device control: in every tool turn of every agent the arguments and the resulting states were right (blind at 50, Cocina all off, two devices on, the bedroom ceiling light after the follow-up; the 40 % light ended at brightness 102 of 255).
    • Streaming: llama_cpp and our component streamed every answer; litellm delivered each answer in one piece, so its TTFS equals the total time and long answers start 1.1 to 1.4 s later (g2, f2). For tool turns the difference is small, because the tool round dominates. Home Assistant starts streaming TTS only after more than 60 characters, and only when the TTS engine accepts streamed input (documented, assist_pipeline/default_pipeline.py); whether the production Wyoming Piper does was not checked.
    • Follow-up: the clarifying question ended in ?, so continue_conversation was true, and the next turn acted on the answer (f1/f1b) in all agents; the topic follow-up (f2b) used the history.
    • llama_cpp and our component are within noise of each other (inferred: medians 0.1 to 0.2 s apart on one backend). First session, for reference: local_openai tool-turn TTFS p50 3.47 s and kiais_conversation 2.13 s, with single outliers in both.
    • No errors or warnings from any of the integrations in the Home Assistant log.
    • Not tested: timers (offered only to a satellite device), the satellite's area context (text runs had no device, hence the "which room?" question), calendar, behaviour when the gateway fails or hangs, real entity names.

    Deployed 2026-11-05

    Done through Home Assistant's config-flow REST API and the websocket API with a short-lived login token (deleted afterwards); no git, chart or cluster change.

    • Config entry llama_cpp, title http://isidoro.isidoro:8080/v1 (in-cluster URL), the existing Kiais client key (kept only in Home Assistant's .storage), model fast. The setup-time test detected streaming (streaming: true); the entry loaded.

Read back and compared with the snapshot taken before: no other field changed (language es, faster-whisper, Piper es_ES-sharvard-medium, wake word unchanged).     Every utterance that is not handled locally, the prompt, the names and areas of all exposed entities and, when a tool runs, their live state go to Kiais and then to whichever provider serves fast (Alibaba and others, see the agent evaluation).
