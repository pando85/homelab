    prusik: CI memory bursts swap-thrash the root NVMe and freeze the API

    Two control-plane outages on 2026-10-12 and 2026-10-13, plus the 2026-09-25 incident, share one mechanism. Node prusik (single-node k3s control plane, embedded etcd, k3s v1.35.8+k3s1 / etcd v3.6.14-k3s1). The first two incidents were attributed to etcd snapshots; they are not.

    TL;DR: CI memory bursts collapse MemAvailable to ~3 GiB, the kernel's reclaim path (swap-out + dirty-page writeback + ZFS ARC shrink) saturates the root NVMe, and that same device holds etcd's WAL, its bolt DB, and /swapfile. etcd's durable writes take seconds instead of milliseconds, the Kubernetes controller Lease cannot renew, k3s calls logrus.Fatalf and exits, and every restart runs an unconditional startup defrag before serving — ~30–75s of API offline per cycle.

    Problem

    What is visible from outside:

    • The Kubernetes API becomes unresponsive for ~30–75 seconds at a time, periodically, in bursts that recur every few minutes until the memory pressure passes.
    • kubectl --context=grigri calls hang or return DeadlineExceeded; kube-system components log leaderelection lost; controllers stall.
    • Components that were mid-flight when k3s died are left in inconsistent state — e.g. a Velero Backup stuck InProgress with orphaned ZFSBackup CRs (docs/troubleshooting/velero-2026-09-25-oom-etcd-outage.md).
    • k3s.service restarts itself (Restart=always), so NRestarts climbs without anyone acting.

    The misdirection: the freezes appear to start "at a snapshot". k3s cron backups run on the default 0 */12 * * * (00:00/12:00 local), and the journal prints Saving etcd snapshot right before a stall, so snapshots look guilty. They were not observed triggering the stalls in these incidents, but they are not exonerated for all future scenarios — see Why snapshots are not the observed trigger.

    Root Cause

    CI memory burst (ci-runner-0 up to 10.7-15 GiB; calypso gVisor runners 16Gi limits each)
  -> MemAvailable collapses to ~3 GiB (62 GiB host, non-CI baseline is flat at 30-35 GiB)
    -> kernel reclaim: swap-out to /swapfile + dirty-page writeback + ZFS ARC shrink 4.9 -> 2.85 GiB
       (against its 5 GiB cap, metal/inventory/host_vars/prusik.yml)
      -> ALL of that I/O is on the root NVMe (SanDisk Extreme 500GB), which also holds:
         - etcd's WAL and bolt DB (/var/lib/rancher/k3s/server/db/etcd)
         - /swapfile (16 GiB, metal swap_file_size_mb: 16384)
        -> etcd durable-write latency spikes: WAL fsync p99 ~1.92s, backend commit p99 ~3.71s
           at 2026-10-13 03:07:30Z (baseline ~1-3ms)
          -> kube-apiserver -> etcd DeadlineExceeded on writes and ReadIndex
            -> the KUBERNETES CONTROLLER Lease cannot renew
               (kube-system Lease, wrangler's leader.RunOrDie — not etcd raft)
              -> logrus.Fatalf -> k3s exits with code 1
                -> systemd Restart=always starts k3s again
                  -> k3s runs an UNCONDITIONAL startup defrag (pkg/etcd Test()) before serving,
                     0.5-4.06s of extra offline time, on the same saturated device
                    -> API offline ~30-75s. Repeat until the memory burst ends.

    Three independent amplifiers make a bad latency blip into a full outage:

    1. Shared device. etcd's durable write path, the swap device, and the root filesystem are the same NVMe. Reclaim I/O is not "background" — it is queued ahead of the WAL fsync.
    2. Overcommitted CI. prusik carried 204.6 GiB of pod limits against 50.7 GiB allocatable (~403%). The scheduler is request-driven, so pods without explicit limits can still be scheduled if their requests fit, but the aggregate limit overcommit means any burst is limited only by the kernel reaching MemAvailable first — and the kernel loses that race against etcd's lease.
    3. Restart cost. k3s defrags at startup before it serves, so each cycle's downtime is latency stall + defrag, not just the process restart.

    Incident windows

    2026-09-25 02:00–02:21 CI Rust builds during the weekly Velero backup window MemAvailable 3.9 GiB (~5.9%), root-NVMe queue depth 218 k3s lost controller lease, exit(1) at 02:20:54; Backup left InProgress

The backups are a possible contributor to I/O load during the 02:30–03:30Z window, but the memory pressure started at 02:06Z, before the backup window. RPC names like "calypso lease" describe what was running, not proof of causal memory pressure — attribution requires per-pod working-set queries (see the runbook).

    The observability blind spot (why CI looked half its real size)

    The container!="" filter used nearly everywhere — and the image!="" filter in kube-prometheus-stack's recording rule — cannot see gVisor sandboxes. A runsc pod exports only two series, both with an empty container label: the pod cgroup (no image label, so image!="" drops it) and the pause/sandbox child cgroup (image="docker.io/rancher/mirrored-pause", so the chart rule keeps only that child). The workload container runs inside the sandbox VM and is never exported as its own cgroup, so there is no named series to fall back on.

    Original incident-window measurement (decimal GB, 10^9 bytes; convert to GiB by dividing by 1.074):

    calypso working set, container!="POD":  3.96 GB (decimal, ~3.69 GiB)   (actual)
calypso working set, container!="":     1.97 GB (decimal, ~1.83 GiB)   (what dashboards showed)

    The second line is the blind spot. Read the first line as an upper bound rather than the true pod total: container!="POD" keeps both the pod cgroup and its sandbox child, so it double counts (row 3 of the table below).

    Re-measured 2026-10-13 across the incident window (02:00–04:00Z, namespace calypso-runners, 2 concurrent autonomous-runner-* pods on prusik). For that namespace the blind spot is worse than "half":

    Query form Result
    per-container (container!="") no series at all — 0 B, while the pod cgroups held 4.20 GB mean / 7.27 GB peak
    chart rule node_namespace_pod_container:container_memory_working_set_bytes 3.65 GB mean, and per sample anywhere from 0.30× to 1.53× of the pod cgroup (mean 0.86×) — it reports the sandbox child cgroup, read at a different instant than its parent, so it skews both ways under a burst
    naive sum(container_memory_working_set_bytes{container!="POD"}) 18.83 GB at 03:07:30Z = pod cgroup + sandbox child added together, 2.3× the real 8.13 GB

    FIXED (2026-10-13): recording rule node_namespace_pod:container_memory_working_set_bytes_incl_gvisor in system/monitoring/resources/gvisor-memory-recording-rules.yaml. It selects the pod-level cgroup series (container="", id!~".*cri-containerd.*", job="kubelet", metrics_path="/metrics/cadvisor") and collapses the duplicates per pod with max by (node, namespace, pod), so gVisor pods are included and a sum over the rule is safe.

    Per-pod memory attribution — dashboards and ad-hoc queries — should use that rule, or the equivalent container="" pod-level form in the runbook below, instead of image!="" / container!="".

    Caveat: it is a pod-level series, so verify per pod and never add it to a named-container sum for the same pod — that is exactly the 2× error above. The two are alternatives, not additive: measured pod-level 3,693,756,416 B vs named-container sum 3,690,844,160 B in monitoring (1.0008×) and 169,762,816 B vs 167,165,952 B in ci-runners (1.0155×).

    Why snapshots are not the observed trigger

    The original hypothesis, and the reason this took three incidents to root-cause.

    • k3s cron snapshots are fast. They stream 130–276 MB in 0.3–0.7s (etcd_disk_backend_snapshot_duration_seconds p99 < 0.64s). A 0.5s copy cannot produce a multi-second API freeze, and it certainly cannot produce one at 03:07 when the schedule fires 00:00/12:00.
    • Internal raft snapshots are a different thing entirely. etcd_debugging_snap_save_total_duration_seconds is the raft-snapshot save (~1.5ms, on a ~10k-entry trigger cadence). It has nothing to do with k3s backups. Confusing the two metric names sends you down the wrong path.
    • The timing is wrong. Slow operations begin minutes after a snapshot, and continue when no snapshot is running. Snapshots are correlated with the outbreak only because 12-hour cron and a Tuesday backup window happen to sit near the CI bursts that actually cause it.
    • Real but irrelevant inefficiency: snapshots do copy dead pages — the DB file is 182 MB allocated vs 66 MB in use (etcd_mvcc_db_total_size_in_bytes vs ..._in_use_in_bytes). That is a 2.7x file-size inefficiency, fixed by compaction/defrag, not a freeze. (It is also what makes startup defrag slow when the device is already saturated.)

    Snapshots were not observed triggering the stalls in these incidents, but they are not exonerated for all future scenarios — if the DB grows large enough or the device degrades, snapshot I/O could become a factor. Monitor etcd_mvcc_db_total_size_in_bytes and the snapshot duration metric.

    Why it is NOT etcd raft leader loss

    etcd_server_has_leader stayed 1 and etcd_server_leader_changes_seen_total stayed 1 throughout — as expected for a single-node member. The leaderelection lost line in the journal is the Kubernetes controller Lease (kube-system Lease, k3s's wrangler leader.RunOrDie), not a raft election. Grepping for "leader" without knowing which elector logged it makes this outage look like an etcd consensus problem, which it never was. The lease is a victim of etcd latency.

    Why the ZFS scrub is not the independent cause

    A monthly scrub of the 25.9 TB datasets pool ran for ~65h and pushed host I/O-PSI to 0.5–0.78. Tempting, but:

    • Healthy windows showed equally high I/O-PSI with no API stalls.
    • The scrub runs on the RAIDZ1 HDDs; etcd's WAL and /swapfile are on the root NVMe. Different physical devices, different queues.
    • The differentiator is memory, not disk: memory-PSI "full" 0.24–0.63, active swap, and MemAvailable < 3 GiB during stalls — and zero when healthy.

    The scrub is a contributor to I/O load, but its role in the outages is unresolved — controls did not independently isolate it. Use memory-PSI plus swap as the discriminator for this mechanism. I/O-PSI alone on this host tells you nothing.

    Why it is NOT an OOM kill

    No node_vmstat_oom_kill and no container_oom_events_total for k3s in any of these windows. The sequence was direct-reclaim stalling + swap thrash (swap used 5.5 → 8.3 GiB at 02:40Z), and then k3s exited by itself (code 1) on lost lease. Nothing was killed. An "OOM?" reflex wastes time here: look for oom_kill, then look at PSI and swap, then look at NRestarts and the journal.

    Major page faults are not proof of direct reclaim. node_vmstat_pgmajfault can rise from file-backed mmap refaults (e.g. etcd's bolt DB pages evicted from page cache and re-read from disk), not just anonymous page swap-in. The pgscan_direct and pgscan_kswapd metrics that would prove direct reclaim are absent from prusik's node-exporter. Use PSI (node_pressure_memory_stalled_seconds_total) and swap rate (node_vmstat_pswpin/pswpout) as the reclaim indicators.

    k3s swap usage: k3s's anonymous Go heap swap usage was measured at ~98MB during the incident, which proves the control plane currently has some swapped pages, but it is not the whole historical picture or the exact mechanism. The file-backed bolt DB mmap pages can be reclaimed and refaulted without being swapped — that is page-cache eviction, not anonymous swap. The swap thrash (5.5 → 8.3 GiB) is the primary mechanism, but the in-memory index latency (550ms) is not uniquely proof of swap — other CPU/GC/query pressure is possible.

    Device names on prusik are NOT stable — read this before writing any query

    NVMe kernel names on prusik change across reboots. The two devices are:

    Model Role Kernel name 2026-09-25 Kernel name after the 2026-10-02 reboot
    SanDisk Extreme 500GB root / (ext4) — holds the etcd WAL + bolt DB and /swapfile nvme1n1 nvme0n1
    FIKWOT FN960 2TB L2ARC / special vdev for the HDD RAIDZ1 datasets pool nvme0n1 nvme1n1

    They will flip again at the next reboot. Therefore:

    • Always identify these disks by model, serial, or /dev/disk/by-id — never by nvmeXnY — in queries, alerts, docs, runbooks, and ad-hoc commands.
    • Verify the current mapping before trusting any historical figure: node_disk_info{instance="prusik"} (maps device → model → PCI path), or on the host lsblk -o NAME,MODEL,SERIAL,MOUNTPOINT.

    Tier 1 — detect it next time

    system/monitoring/resources/etcd-host-memory-rules.yaml (new, wired in system/monitoring/kustomization.yaml): 11 alerts — EtcdTargetDown, K3sEtcdRestarted, EtcdWALFsyncSlow/Critical, EtcdBackendCommitSlow/Critical, PrusikMemoryAvailableLow/ Critical, PrusikMemoryPSIHigh, PrusikSwapThrashing, PrusikRootDiskQueueHigh. They come in pairs on purpose: the etcd metrics are the symptom that pages, the node metrics are the cause that explains it.

    Alert for: durations: warning alerts use for: 5m, critical use for: 2m. These can miss brief outages if k3s restarts faster than the window. K3sEtcdRestarted uses for: 0m as a fast signal — if the restart alert is the first thing you see, the host-side thresholds are too slow: tune them down, do not add more etcd rules.

    Why we needed our own etcd rules at all: kube-prometheus-stack's built-in etcd rules are inert here. They are gated on kubeEtcd.enabled, which is false in system/monitoring/values.yaml (etcd runs as a systemd process, not a mirrored pod), so defaultRules.rules.etcd: true renders nothing. Do not re-enable it expecting coverage.

    system/monitoring/resources/gvisor-memory-recording-rules.yaml (new, wired in system/monitoring/kustomization.yaml) is the other half of detecting it next time: the recording rule node_namespace_pod:container_memory_working_set_bytes_incl_gvisor is what makes the gVisor runners visible to per-pod attribution at all (see The observability blind spot).

    Rejected approaches

    Do not re-propose these; each was considered and rejected on the evidence.

    • Disabling or reducing etcd snapshots — they are not the observed trigger (0.3–0.7s), and they are the recovery path.
    • Raising etcd timeouts / heartbeat intervals — masks the stall, makes the API slower for everyone, and leaves the memory collapse in place.
    • Removing swap before freeing RAM — with 204.6 GiB of limits on 50.7 GiB allocatable, removing the overflow valve converts thrash into OOM kills of whatever the kernel picks, including the control plane.
    • Tuning vm.swappiness alone — changes the balance between reclaim paths, not the total pressure on the shared device.
    • ionice/nice on k3s — one process contains the API server, scheduler, controllers, and etcd; lowering its I/O priority starves exactly what you are protecting.

    If this recurs — how to keep investigating

    Everything below is read-only. SSH commands on prusik are for inspection only (AGENTS.md: no ad-hoc mutation on a remote host); if a command needs root, it is marked [root] and it only reads. All kubectl commands use --context=grigri (the kustomize local context can include other contexts). Do not escalate to local privileged commands; do not execute mutating kubectl commands. The one mutating command this doc names — a scoped, committed, config-only ANSIBLE_EXTRA_ARGS="-t k3s --limit <node>" make cluster — is agent-allowed per AGENTS.md, and only in that form: an unscoped or all-node make cluster, -t k3s without --limit, and any k3s_version bump remain prohibited. It restarts k3s on the targeted node (brief API downtime on the sole control plane), so it is a maintenance action, not part of this read-only investigation path.

    Resolve the root device first — see the device-instability section. Use DEVICE below for "whatever node_disk_info/lsblk says the SanDisk Extreme 500GB is today".

    1. Confirm it is the same mechanism (60 seconds)

    Five discriminating signals. An outage is this mechanism when all of them move together; a healthy baseline is flat on all five.

    Signal Query Healthy This incident Alert
    MemAvailable node_memory_MemAvailable_bytes{instance="prusik"} ≥ 8 GiB (flat) < ~4 GiB (~3 GiB) PrusikMemoryAvailableLow / Critical
    Memory PSI "full" rate(node_pressure_memory_stalled_seconds_total{instance="prusik"}[1m]) 0 0.24–0.63 PrusikMemoryPSIHigh (>0.1)
    Swap rate rate(node_vmstat_pswpout{instance="prusik"}[1m]) pages/s ~0.5 pages/s > 1000 pages/s (storm ~25k) PrusikSwapThrashing
    Root-NVMe queue rate(node_disk_io_time_weighted_seconds_total{instance="prusik",device="DEVICE"}[1m]) single digits > 32 (218 measured, 400+ in a later storm) PrusikRootDiskQueueHigh
    etcd WAL fsync p99 see Prometheus ~1–3ms > 0.25s, peaked 1.92s EtcdWALFsyncSlow / Critical
    etcd backend commit p99 see Prometheus ~1–3ms > 0.25s, peaked 3.71s EtcdBackendCommitSlow / Critical

    Memory-thrash vs a pure disk problem — the decision rule:

    • Memory signals (PSI full > 0.1, swap, MemAvailable < 4 GiB) all zero but root-disk queue and etcd latency are high → it is the device: check SMART, write-cache flush behaviour, thermal throttling, and who else is writing to that NVMe. Do not reach for the CI playbook.
    • Memory signals non-zero → this mechanism. Go straight to attribution (§4).
    • High I/O-PSI with no memory PSI is normal on this host during a scrub — 0.5–0.78 was measured with healthy control-plane latency. Never treat node_pressure_io_* as the trigger.
    • If etcd latency is high and etcd_server_has_leader is still 1 with etcd_server_leader_changes_seen_total unchanged, that is consistent with this mechanism: the killer is the Kubernetes Lease, not raft.

    4. Attribute the memory to a workload

    Query at a point in time at the peak, not max_over_time across a window. A windowed max summarises every short-lived pod at its own moment and reports a total that never existed on the node simultaneously — which is exactly how a gVisor burst gets blamed on a runner that already exited, or missed entirely.

    # Prometheus HTTP API: instant query evaluated AT the peak timestamp
curl -sG http://prometheus.internal.grigri.cloud/api/v1/query \
  --data-urlencode 'query=max by(namespace,pod)(container_memory_working_set_bytes{node="prusik",pod!="",container="",id!~".*cri-containerd.*"})' \
  --data-urlencode "time=2026-10-13T03:07:30Z"

    # Verified pod-aggregate form — USE THIS ON PRUSIK.
# Excludes the root empty Pod series (container="") and excludes named container paths by matching
# id!~".*cri-containerd.*". max by (namespace,pod) picks the aggregate sandbox series if present,
# but this is not a generic guarantee — verify the metadata id filter against your node-exporter
# version. Use point-in-time instant queries, not summing max_over_time.
max by(namespace,pod)(container_memory_working_set_bytes{node="prusik",pod!="",container="",id!~".*cri-containerd.*"})

# Node-total sanity check against the same instant
sum(container_memory_working_set_bytes{node="prusik",pod!="",container="",id!~".*cri-containerd.*"})

# Was anything actually OOM-killed? (In these incidents: no. Answer the question, then move on.)
increase(container_oom_events_total{node="prusik"}[15m])
node_vmstat_oom_kill{instance="prusik"}

    Expect: non-CI baseline flat at 30–35 GiB; anything below that is CI. Check ci-runner-0 first, then calypso-runners, then any pod that started between the two.

    5. The restart + startup-defrag amplifier

    The downtime per cycle is stall + unconditional defrag, so quantify both.

    # Restart count as an outage counter (also exposed as process_start_time_seconds on job="etcd")
systemctl show k3s -p NRestarts

# Each restart: Defragmenting ... before the API comes up (0.5-4.06s measured)
sudo journalctl -u k3s --utc --since "2 hours ago UTC" | grep -iE "Defragmenting|Starting k3s|Main process exited|Failed with result"

    # Every change in process start time = one k3s restart. > 0 is the outage, not a rate.
changes(process_start_time_seconds{job="etcd"}[1h])
up{job="etcd"} == 0

    If the defrag grows steadily across cycles, the DB is accumulating dead pages (etcd_mvcc_db_total_size_in_bytes vs _in_use_...): compact and defrag during a quiet window, not during a stall — defrag on a saturated device is the worst possible time.

    6. Then check the collateral

    Every k3s exit mid-backup leaves state behind. Verify it, do not assume a clean recovery:

    kubectl --context=grigri get backups -n velero | grep -E "InProgress|Queued|PartiallyFailed|Failed"
kubectl --context=grigri get zb -n zfs-localpv | grep -v Done

    Recovery procedure: docs/troubleshooting/velero-2026-09-25-oom-etcd-outage.md and docs/troubleshooting/velero-backup-failures.md.

    Prevention and success criteria

    Fixes are working when, across a CI burst and a backup window:

    1. No k3s lease-loss exits — changes(process_start_time_seconds{job="etcd"}[1h]) == 0 and NRestarts flat; no leaderelection lost in the journal.
    2. etcd latency stays sub-100ms at p99 for WAL fsync and backend commit during CI/backup windows (incident peak: 1.92s / 3.71s).
    3. CI dies at its own boundary — the runner container is OOM-killed or evicted (with low-priority it is first in line) instead of the node thrashing. container_oom_events_total rising on ci-runners while the control plane stays healthy is success, not an incident.
    4. memory-PSI "full" ≈ 0 and swap rate ≈ 0 at the peaks; MemAvailable never under the eviction-soft 4 GiB for more than the 1m grace period.
    5. Alerts fire early — PrusikMemoryAvailableLow, PrusikMemoryPSIHigh and PrusikSwapThrashing precede EtcdWALFsyncSlow, which precedes K3sEtcdRestarted. If the restart alert is the first thing you see, the host-side thresholds are too slow: tune them down, do not add more etcd rules.

    Baseline caveat — read before comparing "before/after". The pre-incident baseline is metrics-only, and the metrics were added while a scrub was running: the scrub started 2026-10-11 00:24 and the node-exporter/etcd series went live 2026-10-11 ~19:11Z. There is therefore no clean pre-scrub window in Prometheus. Treat "healthy" as healthy under I/O-PSI 0.5–0.78 with memory-PSI at zero — which is precisely the comparison that ruled out the scrub. Do not conclude "I/O-PSI is high, so we are still broken" from the scrub overlap, and re-measure the memory/swap floors after the Tier 0/1 changes land rather than reusing these numbers as a target.
