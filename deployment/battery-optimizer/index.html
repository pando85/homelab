    battery-optimizer

    Two workloads of pando85/home-energy-optimizer, deployed from apps/battery-optimizer/ with one image, one PVC and one ConfigMap:

    • pipeline: a CronJob that extracts Home Assistant recorder history and Prometheus samples into an append-only Parquet store, validates it, and builds the 15-minute analysis dataset (Phase B).
    • service: the resident Phase C shadow service (battery-optimizer serve). It reads Home Assistant and Prometheus, solves the MPC plan every 15 minutes and records shadow intents and a shadow-vs-native comparison. It has no actuation path and no write credentials. The production plan and its history live in planning/energy-baseline-production-execution.md.

    The application code, ADRs and domain docs live in the app repository; this page covers only the deployment.

    Design notes and gotchas

    • Why daily with an 8 day HA window. HA's recorder keeps 10 days (purge_keep_days default, nothing overrides it). Rows older than that are gone for good, so the binding rule is "never more than 10 days between two successful runs". Daily with an 8 day lookback tolerates 7 missed runs. The window is deliberately shorter than the retention: the recorder purges nightly, so the oldest chunk of a 10 day window is partly or wholly gone and would raise a coverage gap every night (see the next note). Re-pulling is free because the HA extractor dedups against rows already in the store. Chunk width stays at the CLI default (86400 s); changing it on a live store mints new carry-in anchors.
    • Prometheus extraction is not deduplicated across runs, so the lookback is only 3 days (about 40 KB per day-part). The Prometheus archive has no retention limit, so there is no urgency.
    • Bootstrap. If /data/manifests holds no finished Prometheus extraction (empty PVC), the run extracts Prometheus from PROM_BOOTSTRAP_START (2024-01-01) instead of the 3 day lookback. A manifest is written only by a finished run, so an interrupted bootstrap retries from scratch.
    • Build cadence and window. build is content-addressed and write-once, and measured on the cluster every new extraction changes the dataset id (the part list changes), adding about 4.2 MB per run (~1.5 GB a year if built daily) while nothing consumes the dataset yet. The job therefore builds only on UTC days 01 and 02 of the month (BUILD_ON_DAYS), over the complete months [BUILD_START, first of this month); other days log build skipped. The newest partial month is not in the dataset until the month closes. There is no CLI-side garbage collection of superseded datasets. Run a manual build job if you need one off-cycle (steps 1-3 still run).
    • Permissions. No fsGroup (slow startup on openebs-zfspv). A fresh ZFS dataset is root:root 0755, so the fix-permissions init container chowns the volume root to 65532 (recursively only if the root is not already owned by 65532). See ci-runner-workspace-permission-denied.md.
    • Alerts use release: monitoring, not operator.prometheus.io/instance: prometheus-long-term. kube-state-metrics and kubelet series exist only in the main Prometheus; a rule labelled for prometheus-long-term would load but never fire.
    • No NetworkPolicy. An egress-only policy (DNS, HA 8123, long-term Prometheus 9090) ran from 0.2.1 until 0.3.0 and was removed on 2026-10-25: battery-optimizer is first-party software published from our own repository, and the repo keeps NetworkPolicies for workloads that are not under our control (LLM harnesses). Its only credential is the read-only HA token, and it has no actuation path.
    • The two power signals come from a Gen1 Shelly EM over MQTT at 2 s; the counters still poll. shellyem-main (192.168.86.130) publishes shellies/shellyem-244CAB417668/emeter/{0,1}/power to mosquitto every 2 s (mqtt_update_period: 2) and HA consumes them via apps/home-assistant/config/integrations/shelly_em_mqtt.yaml. Since the 2026-10-27 cutover, grid_power and observed carry those IDs from the mqtt platform, measured as battery_optimizer_input_age_seconds{role="grid_power"} = 2.3 s (was 31.9 s). grid_energy and everything else still arrive over the native integration at 2.2 × 15 s = 33 s, which is correct for a monotonic counter consumed as 900 s deltas — a faster transport would add recorder rows without adding information. The device still carries a permanent error-level push_update_* repair, because CoIoT is multicast-only (peer: "") and nothing forwards it to the HA pod; that is a hygiene item, not a data problem. A faster transport initially looked unusable — the device reboot-looped — but that was mis-diagnosed: the loop needs MQTT and coiot.enabled: false and an HA setup_retry storm, so MQTT is safe as long as CoIoT stays enabled (planning/shelly-em-mqtt-implementation.md). Do not rename these entities or the device: friendly_name is a Prometheus label and part of the archive's series_key. Renaming also moves recorder history — if an ID must ever change hands again, use remove-then-promote (home-assistant-entity-id-handover.md).
    • Never disable CoIoT on that device, and treat HA restarts as a checked operation. With coiot.enabled: false the firmware stops serving /cit/*, HA's initialize() hangs on GET /cit/d, and the next HA restart drops all 14 shellyem-main entities into setup_retry. That happened on 2026-10-26 and cost ~48 min of history (18:02:35Z-18:50:34Z). Since the MQTT cutover the blast radius is narrower but not gone: grid_power and observed would keep working (they come from the broker), while grid_energy — what the dataset is actually built from — would be lost, and MQTT being permanently enabled means the reboot-loop co-factor is always present. Before any HA ConfigMap change (Reloader restarts the pod), verify GET /cit/d still answers 200. Recovery, correct endpoint and pitfalls: shelly-gen1-coiot-disabled-breaks-ha-setup.md.
    • grid_energy still takes ~20 poll timeouts a day; grid_power no longer does. The native /status REST poll occasionally exceeds DEVICE_IO_TIMEOUT = 10 s (~19.7 unavailable rows/day on metadata_id 182 over a 10-day window, dating back before MQTT existed), which flips the whole block to unavailable at T + 33 s + 10 s. In the Prometheus archive those become missing 60 s samples — the 2026-10-27 03:30Z run saw 4420 of ~4526 expected over 3 days and still reported violations=0. Watch for it if the coverage check below ever starts failing: the fix is to move the counters to MQTT too, which has so far not been worth the recorder cost.
    • tariff.yaml and service.yaml are vendored copies of config/ in the app repository (the image carries no config). Update both together; the tariff config hash is part of every dataset id. The CronJob mounts the same ConfigMap at /config and sets BATTERY_OPTIMIZER_SERVICE_CONFIG=/config/service.yaml, so build and extract read battery.commissioned_at and the battery counters from the same service.yaml as the service; set them there on installation day and nothing else needs changing.
    • Coverage gaps fail the Job. From 0.2.1 extract exits 3 when the run's manifest records a coverage gap (HA: empty_chunk, empty_chunk_after_window_filter, chunk_accounting_mismatch, no_rows_for_entity, no_rows_extracted:all; Prometheus: no_samples_extracted, no_series_chunks, series_without_samples_chunks). The data and manifest are kept, but the Job fails and BatteryOptimizerJobFailed fires, so a silent gap is no longer silent. The pipeline does not pass --allow-coverage-gaps (except for the one-off Prometheus bootstrap, whose 2024 history has known holes). If a window legitimately has no data, fix the window rather than opting out.

    Shadow service (Phase C)

    Item Value
    Workload Deployment battery-optimizer-service, 1 replica, strategy: Recreate, same image anchor as the CronJob
    Command battery-optimizer serve, port 8080: /health/live, /health/ready, /status, /plan, /metrics
    Config files/tariff.yaml + files/service.yaml (vendored from the app repo config/) in ConfigMap battery-optimizer-config, mounted at /config. service.yaml uses soc_source: simulated because Home Assistant has no battery entities yet
    HA token the same ExternalSecret as the pipeline, mounted as a file (BATTERY_OPTIMIZER_HA_TOKEN_FILE). Read-only, non-admin; no other credential exists
    Storage the same PVC battery-optimizer-data at /data (RWO on prusik, Recreate avoids two pods). The service writes only /data/service/v1/; the pipeline uses raw/, manifests/ and analysis/, so the paths never collide
    Resources requests 100m / 256Mi, memory limit 512Mi, no CPU limit (observed ~125-150 MiB RSS)
    Probes liveness and readiness on /health/live; generous startup probe. /health/ready returns 503 whenever an input is stale, which would remove the endpoint and stop the scrape exactly when the metrics matter, so alert on battery_optimizer_ready instead
    Service / scrape ClusterIP battery-optimizer:8080 (http); ServiceMonitor labelled operator.prometheus.io/instance: prometheus-long-term (job battery-optimizer, 30 s), so battery_optimizer_* lives in the long-term Prometheus for the multi-week comparison
    Alerts PrometheusRule/battery-optimizer-service (long-term Prometheus): BatteryOptimizerServiceDown, ServiceAbsent, NotReady (30 m), HomeAssistantDisconnected (10 m), GridPowerStale (15 m), PlanStale (1 h), SolveFailures, SinkWriteErrors, SolvesSkipped, HistoryStale, and the climate shadow alerts (rules-service/climate-shadow.yaml)
    Dashboard ConfigMap dashboards-battery-optimizer, Grafana folder battery-optimizer, datasource prometheus-long-term: Battery optimizer shadow service and Battery optimizer climate shadow

    Passive archives (0.3.0). The archive: block of service.yaml turns on two append-only collectors under /data/service/v1/: pvpc_snapshots/ (every state change of the PVPC price sensor, to measure when next-day prices really appear) and weather_forecasts/ (weather.get_forecasts for weather.forecast_home, hourly at HH:05 UTC). The weather query is the single call_service frame the HA guard lets through; every other service call is still refused in code. Watch battery_optimizer_pvpc_snapshots_total, battery_optimizer_weather_forecast_fetches_total{result} and battery_optimizer_archive_last_success_timestamp_seconds. There is no retention yet.

    The shadow store (/data/service/v1/) is private household data and is covered by the same PVC snapshots. Read the comparison with battery-optimizer shadow-report from a pod or a copy of the store; comparison_basis stays no_battery_pre_commissioning until battery telemetry is mapped, and that basis does not satisfy exit gate C.

    Checks without a port-forward:

    kubectl --context=grigri -n battery-optimizer exec deploy/battery-optimizer-service -- \
  python -c "import urllib.request as u; print(u.urlopen('http://127.0.0.1:8080/health/ready').read().decode())"

    Climate shadow (track B2)

    From 0.4.0 the service also runs the climate shadow (climate_shadow: in files/service.yaml): the thermal model and the price-blind comfort MPC of the app repository on live data. Every hour at HH:10 UTC, on its own worker thread, it reads, predicts, plans, records and scores. It is read-only and actuates nothing: the plan is written to the PVC and never sent anywhere, it uses no new credential, and the HA guard still refuses every service call but weather.get_forecasts. App-side reference: docs/service.md#climate-shadow-track-b2 and the preregistration docs/planning/climate-preregistration-2026-27.md in the app repository.

    Input Source
    Room temperatures and setpoints (four thermostats), Aquarea outdoor sensor, outlet target, compressor frequency, heat / DHW / cool power consumed and produced, force-DHW switch, legacy AppDaemon enable and minimum hours, PVPC long-term Prometheus (hass_* series), 30 days fetched at the first run and then incrementally
    input_boolean.comfort_control_enable (regime), input_text.comfort_dhw_plan, input_boolean.comfort_away Home Assistant, through the existing read-only session; each may be absent. Until the comfort controller is deployed they do not exist and every record is regime legacy
    Outdoor forecast the service's own weather archive (weather_forecasts/, fetched at HH:05)

    Failure isolation. A missing prior, site file or config, a Prometheus error or a solver failure is logged (climate shadow not loaded: ..., climate shadow run failed), counted, written as a climate_shadow_error event and retried the next hour. It never changes readiness and never touches the battery planner, which keeps solving every 15 minutes. A healthy job logs nothing; check /status.

    Files.

    Path In git? Content
    /config/climate.yaml, /config/climate-mpc.yaml yes, files/ (public in the app repo too) Comfort rooms, filters, MPC horizon and schedule. Keep them byte-identical to the app repository: their sha256 is part of every climate record's lineage
    /data/analysis/v1/climate-shadow/priors/<prior>/prior.json no, PVC only The season prior (model parameters fitted on household data), content-addressed and write-once; climate_shadow.prior names it
    /data/climate/site.yaml no, PVC only Private site file (coordinates, reference station). Never commit it or paste it anywhere
    /data/service/v1/climate_{decisions,scores,days,models}/ no The shadow's records, written by the service; covered by the PVC snapshots and just pull-store

    The prior and the site file stay out of this public repository and out of Vault: they are not credentials, and the job reads them from the data directory only. They are copied onto the PVC once from the owner's workstation, which keeps them in ~/data/battery-optimizer-cluster (the just pull-store copy of the PVC).

    Install or refresh the prior. In the app repository, on a clean checkout of the deployed commit, with BATTERY_OPTIMIZER_DATA_DIR=~/data/battery-optimizer-cluster:

    uv run python hack/climate_shadow_prior.py --feature-set <climate feature set id> \
  --dataset ~/data/battery-optimizer-cluster/analysis/v1/<dataset id> --season S3
# prints the prior id and writes analysis/v1/climate-shadow/priors/<id>/prior.json

    Copy it and the site file onto the PVC through the running pod (the image has tar; /data is the only writable path):

    PRIOR=<id>; SRC=~/data/battery-optimizer-cluster
tar -C "$SRC" -cf - "analysis/v1/climate-shadow/priors/$PRIOR/prior.json" climate/site.yaml \
  | kubectl --context=grigri -n battery-optimizer exec -i deploy/battery-optimizer-service -c service -- \
      tar -xf - -C /data --no-same-owner

    then set climate_shadow.prior: "<id>" in files/service.yaml and merge. A prior directory can stay on the PVC after it is replaced: only the configured one is loaded.

    Go-live of the comfort controller. On the day the comfort controller takes over, set climate_shadow.go_live: "YYYY-MM-DD" (local date) in files/service.yaml and merge. Without it there is no new-window verdict (the first comfort record is only reported as a provisional date); the new window starts 7 days after go_live. Do not change the prior, the comfort rooms or climate-mpc.yaml around go-live: any of them starts a new lineage, which the gates evaluate apart.

    Read the gate report (from the store on the PVC, no network; it prints private figures, keep the output local):

    kubectl --context=grigri -n battery-optimizer exec deploy/battery-optimizer-service -c service -- \
  battery-optimizer climate-shadow-report            # add --format json for the raw report

    Per window (legacy, new) it shows the valid heating days and weeks (6 weeks are needed, else every criterion is UNDETERMINED), each preregistered criterion with its value, threshold and PASS / FAIL / UNDETERMINED, RMSE, persistence RMSE, skill and bias at 1, 6, 12 and 24 h, the daily heat MdAPE, solver statuses and times and the top-offset share. /status (climate_shadow) shows the prior, model hash, last run, scoring queue, error, go-live and the two verdicts.

    When to refit the prior. The weekly ua/q0 re-estimation runs inside the service; the prior stays fixed through both preregistered windows. Fit a new one for the next heating season, or earlier only when a model input changes: the outdoor sensor or the heat measurement, the comfort rooms or their thermostats. A change of the schedule, the water curve or the machine limits is an edit of climate-mpc.yaml (vendor it from the app repository), not a refit. Record either in the app repository's regime log.

    Expected after a deploy. The first run happens at the next HH:10 (or at once if the pod starts after HH:10). battery_optimizer_climate_shadow_up is 0 until then and 1 afterwards; runs_total{result="planned"} and solves_total{status="optimal"} grow every hour; regime{regime="legacy"} is 1; the first refits_total is counted at the first run. Accuracy series (rmse_kelvin, skill_ratio, ...) appear once the first origins are scored, 24 to 48 h later, and the gates stay UNDETERMINED until 6 valid heating weeks are in a window.

    Alerts (rules-service/climate-shadow.yaml): BatteryOptimizerClimateShadowDown (up == 0 for 2 h), ClimateShadowNoRun (no run for 2 h), ClimateShadowRunErrors (more than 2 errors in 6 h), ClimateShadowSolveFailures (infeasible or error solves) and ClimateShadowNoState (the climate series have gaps). Dashboard: Battery optimizer climate shadow (runs, solver, accuracy per horizon, valid weeks, gates, regime).

    First run (2026-10-25)

    Manual Job from the CronJob on an empty PVC: success in 5m46s including the full Prometheus bootstrap (1028 parts, 5.84 M rows), peak working set about 1.15 GiB (requests 768 Mi, limit 2 Gi), about 0.54 core peak, 41.5 MiB on the volume afterwards. Steady-state runs only re-pull 8 days of HA history and 3 days of Prometheus. The PVC is the store of record. A migration of the manual ~/data/energy-baseline store was checked on 2026-10-25 and is not needed: every HA row in it (39 distinct) is already in the PVC (54), Prometheus is re-extractable, and the OMIE backfill is public. The local store stays frozen as the record behind the offline evaluation runs.

    Container logs carry one httpx INFO line per request (roughly 1000 for the bootstrap), so kubelet log rotation can drop the early step N/4 lines of a long run; Loki keeps the full stream.

    Operate

    # State
kubectl --context=grigri -n battery-optimizer get cronjob,job,pvc,externalsecret
kubectl --context=grigri -n battery-optimizer logs job/<job-name> -c pipeline

# Run one pipeline outside the schedule (e.g. after fixing a failure)
kubectl --context=grigri -n battery-optimizer create job --from=cronjob/battery-optimizer-pipeline battery-optimizer-pipeline-manual-<n>

    Local analysis copy (read-only on the cluster; streams the PVC out of the service pod, validates it, and syncs it into a separate directory — never into the frozen ~/data/energy-baseline):

    cd ~/home-energy-optimizer && KUBE_CONTEXT=grigri just pull-store   # ~/data/battery-optimizer-cluster

    Bumping the image is a Renovate PR changing tag in apps/battery-optimizer/values.yaml. A new code version changes every dataset id, so expect one extra dataset on the next build.

    Growing the volume: raise spec.resources.requests.storage in templates/pvc.yaml (allowVolumeExpansion is on). Never delete the PVC; Prune=false and Retain protect it.

    App Repository Notes

    • Code lives in pando85/home-energy-optimizer (moved history-preserving from scripts/energy-baseline on 2026-10-24/25). Releases are cut with just release; the auto-tag workflow uses the repo secrets PAT and GPG_PRIVATE_KEY (both set). Renovate (Mend app) automerges.
    • Local analysis env: a gitignored .envrc (direnv) sets UV, KUBE_CONTEXT=grigri and BATTERY_OPTIMIZER_DATA_DIR=~/data/battery-optimizer-cluster.
    • The load-forecaster and price-outlook improvement plans (app repo docs/planning/) are parked since 2026-10-25; resume triggers are in the load plan §6 (spring 2027 cooling season, battery commissioning, household or rule change). Evaluation results stay in the private data directory.
    • Owner decisions, do not re-raise: taxes in tariff.yaml (PVPC, not important); license, DCO and GHCR bootstrap are done or not needed.
